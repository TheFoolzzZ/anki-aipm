## 1. 课程边界

保留知识库原来的 9 个大章，在章节中组织牌组；学习顺序可以跨章节组合。全库扫描得到 70 篇 Markdown，其中第9章一个文件包含 440 个问题，不能简单以文件数平均分配卡数。

以下数量是**首轮编辑预算**，不是已经生成或审校完成的卡片数量。初始共 360 张核心卡；扩展卡不预设总量，依据学习反馈和内容质量增加。

| 章节 | 核心卡预算 | 核心制卡方向 | 扩展内容 |
| --- | ---: | --- | --- |
| 1 入门Ai产品经理 | 20 | 职责区别、交付、沟通与问题定义 | 百问中的重复或低优先知识 |
| 2 深度了解AI PM | 25 | 能力边界、跨团队协作、技术理解层次 | 岗位深挖与复杂交付场景 |

## 3. 16 周主题路线

工作日每天 30 分钟；每周默认新卡 20–30 张以内，复习优先，超预算则顺延单元。下表描述主题推进，不承诺每周清空一个原章节。

| 周 | 本周主题与来源 | 本周能完成的表达/判断 | 周末面试主题 |
| --- | --- | --- | --- |
| 1 | 第1章核心；第2章角色与任务 | 说清 AI PM 和传统 PM 的共同点、额外责任 | 如何定义一个值得做的 AI 功能 |
| 2 | 3.1–3.5 模型基础 | 解释模型能力与不确定性，不靠术语堆砌 | 模型演示很惊艳，为什么还不能直接上线 |
| 3 | 3.7–3.9、3.14；5.1 成本入门 | 说明 Prompt、上下文、Token 与成本的关系 | 如何减少上下文成本而不损害效果 |
| 4 | 3.10、3.16、3.20、3.11 前半 | 解释文档进入检索系统的路径与切分取舍 | 为企业规章设计检索方案 |
| 5 | 3.11 后半、3.6；3.23/3.25 归因入门 | 区分检索问题、生成问题与适配需求 | RAG 答错了，如何排查、是否要微调 |
| 6 | 3.12、3.17、3.24 | 区分工具调用、固定工作流和 Agent | 查询与执行任务，哪些可以自主、哪些要控制 |
| 7 | 3.13、3.15、3.21；第4章 | 说明状态、复用步骤、原型验证与交付边界 | 如何把可运行 Demo 变成可验收流程 |
| 8 | 3.18、3.19、3.22 | 解释协议解决的问题及剩下的工程责任 | 多系统 Agent 如何接入工具并反馈状态 |
| 9 | 3.23、3.25 系统学习 | 设计评估集、评分标准、切片与门禁 | 更换模型后如何证明没有严重退化 |
| 10 | 5.2–5.4；第2章交付方法 | 从业务问题到方案、证据与优先级 | 值不值得使用 AI，如何验证需求 |
| 11 | 5.5–5.7 | 写清 AI PRD 的效果、边界和兜底 | 不确定性如何进入需求文档和验收 |
| 12 | 3.26 FDE-Ontology | 区分业务对象、动作、权限与审计 | 将一个现实业务流程建模成可执行系统 |
| 13 | 6.2 企业级知识库、6.4 智能客服 | 从用户、数据、评估到人工接管设计方案 | 企业知识库/客服产品综合面试 |
| 14 | 6.1 AIGC、6.3 OpenClaw、6.5 编程Agent | 比较不同 Agent 产品的价值与失败模式 | 编程或办公 Agent 如何衡量可用性 |
| 15 | 第7章；第9章方法卡 | 讨论单位经济、定价与商业验证 | 用户喜欢但成本很高，商业上怎么办 |
| 16 | 全路径综合；第8章经核对的讨论 | 在新约束下组织完整方案并回应反对意见 | 综合模拟面试 + 下一轮个人补强路线 |

第9章每周可抽一个讨论题，第8章从中后期按主题选择，不增加固定背诵任务。第2章剩余核心卡穿插第10–11周，避免第一周只有职业介绍而迟迟碰不到技术。

熟悉程度调整：

| 模块诊断 | 路径变化 | 记忆记录 |
| --- | --- | --- |
| 没接触或无法解释 | 先微课，再基础卡 | 从真实首次复习初始化 |
| 定义会、场景判断弱 | 减少解释阅读，保留边界与场景卡 | 已验证卡正常调度，未答卡仍为未学 |
| 做过项目且诊断通过 | 优先选型、失效场景、指标与追问 | 不给整章批量写入“已掌握” |

## 4. 第一周具体安排

| 日期 | 12分钟复习 | 5分钟微课 + 8分钟新卡 | 3分钟表达 + 收尾 |
| --- | --- | --- | --- |
| 周一 | 无到期卡时用本段完成 onboarding 与诊断 | 第1章角色差异，最多 4 张 | “我理解的 AI PM 额外责任” |
| 周二 | 处理周一产生的到期和重学 | 第2章能力边界，最多 4 张 | 区分“需要理解”与“需要亲手实现” |
| 周三 | 按真实到期队列 | AI PM 的交付任务，最多 4 张 | 用一个项目说明问题、目标、验收 |
| 周四 | 按真实到期队列 | 基础沟通和需求澄清，最多 4 张 | 给一个含糊需求补关键问题 |
| 周五 | 按真实到期队列 | 本周错题变式或最多 4 张新卡 | 90秒总结，确认周末面试题域 |
| 周六 | 建议 5–10分钟，无新卡 | 另做 25–35分钟面试训练 | 只选最重要的 1–3 个薄弱点 |
| 周日 | 建议 5–10分钟，无新卡 | 可选 10分钟重答 | 查看下周主题，可调整计划 |

星期几不决定固定卡片复习间隔。表中“周一产生”只说明来源，具体哪天复习由 FSRS 依据真实评分计算。

## 5. 卡片字段契约

| 字段 | 用途 |
| --- | --- |
| `card_id` / `revision` | 稳定身份与不可变内容版本 |
| `home_lesson_id` | 唯一主归属；大章节由学习单元确定 |
| `concept_ids` | 跨章节去重、面试覆盖与薄弱点关联 |
| `kind` | recall / contrast / scenario / calculation / diagnosis |
| `prompt` | 独立可理解的问题，不泄露答案 |
| `answer_short` | 一句话或极短段落的最小答案 |
| `required_points` | 1–3 项评分点 |
| `explanation` / `pitfalls` | 折叠解释与误区 |
| `source_refs` | 源文件、标题路径、段落、哈希、必要的行号 |
| `provenance_type` | source_paraphrase / teaching_extension / verified_correction |
| `valid_as_of` / `recheck_after` | 时效卡核对日期；稳定概念可为空 |
| `estimated_seconds` | 初始时间预算，后续由实际记录校准 |
| `editorial_level` | foundation / application / advanced，区别于 FSRS difficulty |
| `status` | draft / needs_verification / published / retired |

来源行号用于设计稿人工核对；正式入库同时保存源版本哈希和段落内容，避免源文件更新后行号失效。复杂题的可接受答案与错因放在量表里，不用单一字符串做精确匹配。

## 6. 14 张代表性样卡

以下全部为设计样稿，状态为 `draft`。数字、企业知识服务等情境如非原文实例，明确列为教学设定；它们不冒充真实项目数据。技术攻克是主要样例来源。

### C01 · RAG 与微调的边界

- 归属：技术攻克 → 3.11 RAG；类型：场景判断；概念：`rag-vs-finetuning`；预计 45 秒。
- **正面**：企业内部政策每周更新，需要回答时说明依据。为什么通常先考虑 RAG，而不是仅靠微调记住政策？
- **最小答案**：RAG 可以通过更新检索资料来接入新政策，并保留答案依据；仅靠微调更新知识需要再训练，也不天然提供来源。
- **必答点**：更新知识的机制；可追溯依据。
- **误区**：RAG 不保证答案准确，仍需要检查资料版本、检索和生成；也不排斥同时使用微调。
- **来源**：[3.11「RAG vs 微调」](kb://第3章-技术攻克/3.11-讲透-RAG.md:472)，参考原文 472–498 行。
- 来源处理：原文概念改写；“每周更新”是教学情境；去掉原文成本与效果的过度普适表述。

### C02 · 混合检索适用性

- 归属：3.11 RAG；类型：场景判断；概念：`hybrid-retrieval`；预计 40 秒。
- **正面**：搜索既包含口语化描述，又包含精确文档编号时，为什么可考虑关键词与向量混合检索？
- **最小答案**：向量检索补语义相似，关键词检索补精确词项匹配，融合后兼顾两类需求。
- **必答点**：语义匹配；型号/词项精确匹配。
- **误区**：混合检索不是必然提升，需在代表性查询集上验证。
- **来源**：[3.11「混合检索」](kb://第3章-技术攻克/3.11-讲透-RAG.md:209)，209–227 行。
- 来源处理：原文概念改写；验证要求为教学延伸。

### C03 · Chunk 大小的取舍

- 归属：3.11 RAG；类型：对比；概念：`chunk-size-tradeoff`；预计 35 秒。
- **正面**：RAG 的文本块过小与过大，分别容易带来什么问题？
- **最小答案**：过小可能丢失必要上下文，过大可能混入无关内容、降低检索针对性并增加上下文负担。
- **必答点**：信息完整性；噪声与聚焦程度。
- **误区**：把某篇教程的固定 Chunk Size 当作所有业务的最优参数。
- **来源**：[3.11「文本切分」](kb://第3章-技术攻克/3.11-讲透-RAG.md:110)，110–143 行。
- 来源处理：原文概念改写，不要求记住教程中的建议数值。

### C04 · Recall@K 的分母

- 归属：3.23 技术指标，关联 3.11；类型：计算；概念：`recall-at-k`；预计 45 秒。
- **正面**：某次查询共有 5 个相关文档，Top-10 检索结果中找到了其中 3 个。Recall@10 是多少？
- **最小答案**：3 ÷ 5 = 60%。
- **必答点**：分母是全部相关文档数 5，不是返回数 10。
- **误区**：3 ÷ 10 对应这组设定下的 Precision@10，不能混用。
- **来源**：[3.11「检索效果评估」](kb://第3章-技术攻克/3.11-讲透-RAG.md:369)，369–375 行。
- 来源处理：公式来自原文，5/10/3 是教学设定；不沿用该表中其他可能有歧义的指标口径。

### C05 · 忠实度与相关度

- 归属：3.11 RAG；类型：对比；概念：`faithfulness-vs-relevance`；预计 35 秒。
- **正面**：回答完全依据检索资料，但没有回答用户真正问的问题。哪两个评价维度应分开看？
- **最小答案**：忠实度看回答是否得到资料支持，回答相关度看是否切题。忠于资料不等于回答了问题。
- **必答点**：资料支持；是否切题。
- **来源**：[3.11「生成效果评估」](kb://第3章-技术攻克/3.11-讲透-RAG.md:378)，378–385 行。
- 来源处理：原文概念改写，题目场景为教学设定。

### C06 · 工具调用由谁执行

- 归属：3.17 Function Call；类型：概念；概念：`tool-execution-boundary`；预计 30 秒。
- **正面**：模型输出了工具名称和参数，是否代表业务操作已经完成？
- **最小答案**：没有。模型提出调用，应用程序校验并执行工具，再把执行结果交回模型。
- **必答点**：生成调用与执行动作分离；以工具真实结果判断完成。
- **误区**：把模型说“已完成”当作数据库已经写入的证据。
- **来源**：[3.17「Function Call 定义」](kb://第3章-技术攻克/3.17-Function-Call.md:9)，9–27 行及 89–141 行。
- 来源处理：原文概念改写。

### C07 · 工具调用权限

- 归属：3.17 Function Call；类型：场景判断；概念：`tool-authorization`；预计 35 秒。
- **正面**：只在 Prompt 里要求“用户只能查看自己的文件”，能否构成数据权限控制？
- **最小答案**：不能。执行工具的服务端还必须依据已验证用户身份检查文件访问范围，不能依赖模型自觉遵守。
- **必答点**：服务端校验；身份与数据范围匹配。
- **误区**：过滤模型可见的工具列表是辅助控制，不替代真实执行授权。
- **来源**：[3.17「安全与权限设计」](kb://第3章-技术攻克/3.17-Function-Call.md:551)，551–582 行。
- 来源处理：原文概念改写，Prompt 场景为教学设定。

### C08 · MCP 与 Function Call

- 归属：3.19 MCP；类型：对比；概念：`mcp-vs-function-call`；预计 40 秒。
- **正面**：Function Call 与 MCP 各自主要解决什么问题？
- **最小答案**：Function Call 让模型输出结构化的工具调用意图；MCP 标准化应用与外部工具、资源之间的连接与发现方式。
- **必答点**：调用意图与参数；标准化工具/资源接入。
- **误区**：支持 Function Call 的模型，不代表所在应用天然已经实现 MCP 连接和权限治理。
- **来源**：[3.19「MCP vs Function Call」](kb://第3章-技术攻克/3.19-MCP.md:146)，146–160 行，结合 61–144 行角色说明。
- 来源处理：对原文类比进行限缩改写；避免沿用“任何模型都自动发现工具”的过度概括。发布前对照当前 MCP 官方架构进一步审校。

### C09 · Evals 的最小组件

- 归属：3.25 Evals；类型：概念；概念：`eval-core-components`；预计 45 秒。
- **正面**：Evals 中，Dataset、Grader、Runner、Reporter 分别负责什么？
- **最小答案**：测试材料、评分、执行测试、汇总分析。
- **必答点**：准确对应四个组件的职责；不要求复述长定义。
- **误区**：只有一批测试问题，还不是可以持续运行的完整评估过程。
- **来源**：[3.25「四个核心支柱」](kb://第3章-技术攻克/3.25-Evals.md:130)，130–137 行。
- 来源处理：原文压缩改写。这张对应关系卡可在试学发现负担过高时拆成两张。

### C10 · RAG 错答诊断

- 归属：3.25 Evals；类型：诊断；概念：`rag-failure-attribution`；预计 50 秒。
- **正面**：RAG 回答错了，为什么应先检查进入模型的检索上下文，再决定怎么改 Prompt？
- **最小答案**：需要先分清证据是否被检索并送入模型；证据缺失、模型误用证据、资料本身过时，需要不同修复方式。
- **必答点**：检查实际上下文；根据错因区分修复层。
- **误区**：某个自动指标达标，不足以排除链路中的其他问题。
- **来源**：[3.25「检索问题还是生成幻觉」](kb://第3章-技术攻克/3.25-Evals.md:395)，395–410 行。
- 来源处理：将原文单一路径示意改写为诊断起点，不把“忠实度达到 1 就只剩文档问题”作为定理。

### C11 · 裁判的位置偏差

- 归属：3.25 Evals；类型：误区与诊断；概念：`judge-position-bias`；预计 35 秒。
- **正面**：用模型比较答案 A 与 B 时，为什么可以交换展示顺序再评一次？
- **最小答案**：检查裁判是否偏好某个展示位置，降低位置对结论的影响。
- **必答点**：展示顺序可能影响评分；对调用于检查偏差。
- **误区**：两次结论一致不等于裁判绝对正确；仍需明确量表和人工校准。
- **来源**：[3.25「裁判偏见及对策」](kb://第3章-技术攻克/3.25-Evals.md:275)，275–284 行。
- 来源处理：原文概念改写，人工校准为教学延伸。

### C12 · 一次文本请求的成本

- 归属：AI产品设计 → 5.1 Token成本；类型：计算；概念：`token-cost-calculation`；预计 50 秒。
- **正面**：假设输入价格为 2 元/百万 Token，输出为 8 元/百万 Token。一次请求输入 4,000、输出 1,000 Token，费用是多少？忽略缓存、推理及其他计费项。
- **最小答案**：0.016 元，即 4,000×2÷1,000,000 + 1,000×8÷1,000,000。
- **必答点**：输入输出分开计费；统一“百万 Token”的计价单位。
- **误区**：这里的单价只是练习设定，不代表当前任何模型的真实报价。
- **来源**：[5.1「API计费的基本单元」](kb://第5章-AI产品设计/5.1-Token成本.md:20)，20–33 行。
- 来源处理：原文公式 + 明示教学设定。

### C13 · AI PRD 如何描述质量

- 归属：AI产品设计 → 5.5 AI PRD；类型：场景判断；概念：`ai-prd-acceptance`；预计 45 秒。
- **正面**：为什么“模型能正确回答用户问题”不足以作为 AI PRD 的验收标准？
- **最小答案**：输出存在波动，需要定义评估范围、正确性判定和可测量的达标条件，才能验证质量。
- **必答点**：可测量条件；明确测试与判定口径。
- **误区**：孤立写一个“准确率≥90%”，却不说明数据集与正确答案口径，仍无法可靠验收。
- **来源**：[5.5「AI PRD与传统PRD的本质区别」](kb://第5章-AI产品设计/5.5-如何写AI-PRD.md:7)，7–28 行与 38–46 行。
- 来源处理：原文统计验收思想 + 评估口径的教学延伸。

### C14 · Agent 评估不能只看终点

- 归属：3.25 Evals；类型：因果解释；概念：`agent-trajectory-evaluation`；预计 40 秒。
- **正面**：Agent 最后给出了正确结果，为什么还需要查看它的工具调用轨迹？
- **最小答案**：正确结果可能伴随多余调用、错误参数或不恰当操作；还要判断过程的成本、可靠性和边界。
- **必答点**：终点正确不足以证明过程合理；至少举出一种需要检查的过程问题。
- **误区**：这里指可观察的调用、状态和结果，不要求读取模型隐藏的内部思维过程。
- **来源**：[3.25「轨迹评估」](kb://第3章-技术攻克/3.25-Evals.md:415)，415–435 行。
- 来源处理：原文概念改写；“轨迹”限定为可观察行为。

## 7. 两道面试设计样题

### I01 · 企业知识库：答对与上线之间

适合 RAG / Evals 周，涉及 C01、C02、C05、C10、C13。以下均为教学设定：一家企业的客服知识每天更新；内部演示不错，但真实用户投诉回答过时，部分问题引用了无关内容。

**主问题**：作为 AI PM，你先如何定位问题、定义改进目标，而不是直接要求“换一个更好的模型”？

追问顺序：先让用户自行组织排查 → 要求说出可观察证据 → 增加“不能显著增加延迟”的限制 → 询问如何验收与灰度。

评分观察：是否区分文档、索引更新、检索、上下文组装和生成；是否提出代表性评估集与分层指标；是否考虑版本、生效时间和用户体验。允许多条合理诊断路径，不要求照读模板。

报告样式：

> 你区分了检索与生成，但没有说明如何确认新政策已经进入索引。请补充一个可验证检查，并说明出现新旧政策冲突时的处理策略。

这只是报告文案示例，不是用户已发生的面试表现。正式报告须附真实回答时间戳与引用。

### I02 · 会查询资源的 Agent 是否应该直接执行高风险操作

适合 Agent / Function Call / Workflow 周，涉及 C06、C07、C14。

**教学设定**：企业助手可以查询资源状态，业务方希望它根据一句自然语言直接执行一项有外部影响的操作。

**主问题**：你如何划分查询、建议、确认和提交的交互与执行边界？

追问：用户选错工作空间如何处理 → 工具超时后重试会不会重复执行 → 何时应由人确认 → 如何定义任务成功及异常回退。

评分观察：是否区分模型意图与真实执行；是否想到身份、数据范围、幂等与失败状态；是否依据业务风险讨论确认环节；是否有可观测的结果证据。具体情境是教学延伸，不冒充源文已有案例。

该题的幂等与业务异常属于扩展考点，应先检查用户是否已学到相应材料；未学习则用于教练讲解，不计为正式扣分。
